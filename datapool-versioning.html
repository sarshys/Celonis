Why Data Pool Versioning Matters in Production

17 AUG 2026 · 6 MIN READ · H

A data pool is the container that holds your extractions, transformations and data model for a source system. It's easy to treat it like any other piece of config — edit it directly, save, move on. That works fine right up until a transformation change breaks a downstream model in production and nobody can say exactly what the pool looked like an hour before.

That's the gap versioning closes. It's not just a "nice to have" changelog — it's what lets a change be reversible instead of permanent.

What actually gets versioned

When you save a version of a data pool, Celonis snapshots the parts that define how the pool behaves:

  • Data jobs — every extraction and transformation
  • The data model (aside from name mappings)
  • Data pool parameters
  • Replication Cockpit configuration

Source system credentials and a few other sensitive settings deliberately aren't included, for security reasons — versioning captures configuration, not secrets.

Draft, save, revert

A new data pool starts in draft. Once you save it, that becomes version 1.0.0 and is marked as the latest version. From there, every change you make lives in draft again until you explicitly save a new version — at which point you choose whether it's a major, minor, or patch update, and the version number increments accordingly. A jump like 2.2.4 tells you at a glance: second major revision, two minor updates on top of it, four patches since.

You can hold up to 100 versions per data pool, diff any two of them to see exactly what changed, and revert to an earlier one if a deployment goes wrong. That last part is the actual safety net — instead of trying to manually undo a bad transformation change under pressure, you load the version from before the change existed.

The same discipline applies one layer up — object-centric data models (OCDMs) get their own versioning and deployment flow, letting you deploy a specific version to development or production and re-deploy an earlier one if something goes out wrong.

Where this actually saves you

In practice, versioning earns its keep in three moments:

  • Mid-deployment rollback — a transformation update introduces a bug that only shows up once real data flows through it. Reload the last known-good version instead of debugging live.
  • Parallel work — more than one person touching the same pool without a shared version history is how conflicting changes quietly overwrite each other.
  • Audit and accountability — being able to say precisely what changed, when, and in which version turns "something broke recently" into a two-minute diff instead of a guessing game.

None of this is complicated to set up. It just has to be a habit before something breaks, not a process you improvise while it's already broken.
